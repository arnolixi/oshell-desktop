## 逐项计时与分片规则

原来的串行专项计时已由用户取消并移除。初始权重来自本机 Windows 普通测试的完整 JSON 日志：211 个顶层测试，包耗时 93.523 秒。它不是竞态计时，仅用于初始调度；Linux 使用同一组估算权重，但测试清单按平台二进制独立发现。

最慢项为 WebDAV 多节点合并（12.90 秒）、升级辅助程序生命周期（12.18 秒）、同步创建/下载/冲突（7.18 秒）、冲突草稿重启（5.56 秒）。竞态检测显著放大真实密码派生计算开销，因此不降低密码派生强度，使用独立进程并行执行。

`scripts/core_test_shards.py` 读取当前测试二进制的完整清单，按预计耗时从长到短，将测试分配给累计时间最短的分片。新增测试使用默认权重，不能因缺少历史时间而漏测。顶层测试包含其全部子测试，不重复累计子测试时间。

Windows core 竞态测试二进制由容器统一预编译；Linux 各分片复用编译缓存，在容器中构建本片使用的二进制。每个平台分成 4 片。Linux 在 4 个独立 Ubuntu Runner 的容器中执行，Windows 在 4 个原生 Windows 任务中分别执行。Linux 普通回归单独运行，避免分片争用同一台机器的 CPU。每次显式使用 `-test.count=1`，执行原有测试及其跳过条件。PTY / ZMODEM 竞态测试、普通全量回归和桌面测试继续执行。

每片上传原始 JSONL 及清单，汇总任务要求两平台各 4 片、提交一致、测试发现清单一致、每个测试恰好执行一次、所有测试完成、包成功结束，且报告与原始日志一致。失败退出、超时、截断日志、缺失/重复分片都会阻止发布。原有测试主动跳过的场景单独列出；没有 Swift helper 时不能声称真实 Swift 互通已经通过。

当前竞态耗时及来源记录在 `scripts/core-race-timings.json`。首轮官方 Runner 测得 Windows 四片为 242.61、100.65、247.64、257.84 秒（顶层测试耗时总和），暴露了普通测试权重的不均衡；改用真实竞态权重重新分配。不能将普通测试耗时标记成竞态耗时，也不能将测试结果缓存代替执行。

## 容器与缓存

所有编译任务使用 GitHub 官方 `ubuntu-24.04` Runner，由 `scripts/build-on-runner.sh` 调用 Docker。Windows 执行任务没有 Go 构建步骤；升级辅助程序和 JSON 日志适配器也由容器预编译。测试包携带提交 SHA，执行前校验。

- `.github/docker/build.Dockerfile` 缓存 Ubuntu 24.04 系统依赖，包括 MinGW 交叉编译器及 Linux 图形测试运行库，每月刷新系统包。
- `actions/setup-go` 仅安装工具链，只读挂载 `/opt/go`，所有编译在容器内执行。
- `actions/cache` 保存模块、编译缓存、原生资源，Docker Buildx 的 `gha` 后端保存系统镜像层。缓存按任务与依赖区分，适配每次新建的官方 Runner。Go 自动按工具链/平台/编译输入隔离缓存，依赖仍由 `go.sum` 校验。
- Windows / Linux 发布包在同一容器内顺序构建，避免临时生成的嵌入资源冲突。Windows 额外编译带真实嵌入资源的测试，在真实 Windows 验证。
- 容器仅挂载工作区、只读工具链及缓存目录，不挂载宿主 Docker socket 或凭据。退出或取消时恢复工作区所有权。
- 推送、PR 和手动运行均进入官方临时 Runner，不依赖组织服务器；Linux 回归与打包并行开始。分支新提交取消旧任务，标签不自动取消。

首次运行需初始化镜像和 Windows 交叉编译竞态缓存，不能代表热缓存速度。比较优化耗时应同时报告冷缓存和热缓存；清理 Actions 缓存只影响后续构建速度，不涉及用户配置。
